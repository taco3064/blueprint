'@kekkai/blueprint': minor

Add a first-class post-adoption lifecycle: `blueprint upgrade` and `blueprint remove`.

`npx @kekkai/blueprint@latest upgrade` uses the running package as the only target authority. It reads the repository's lifecycle checkpoint from the new `.blueprint-lifecycle.json`, or proves it from the installed package and config shape on a repository adopted before lifecycle state existed, and resolves the structured upgrade operations of every release across the whole source → target interval before anything runs: canceled and superseded operations are removed, the rest are ordered by their requirements. It then records the pending upgrade, moves `@kekkai/blueprint` to the target through the detected package manager, continues with that installed copy, runs deterministic migrations by reconciling every adopted application through `blueprint init`, writes one resolved `blueprint-upgrade.md` playbook when semantic work remains, and records the new lifecycle only after `blueprint inspect --baseline` and `blueprint doctor` pass in every adopted application. `--dry-run` shows the complete plan without mutation, `--complete <operation-id>` records verified semantic work, and a pending upgrade resumes without repeating completed operations.

Starting an upgrade requires a Git worktree without uncommitted changes, and no upgrade runs while an authoring or topology-transformation workflow is unfinished. Downgrades and sources before 3.2.0 are refused, and so is an application that resolves a newer package than the running release, or a mix of package versions. When the record already matches the target but an application resolves an older package or none, `upgrade` reinstalls the target instead of reporting it current: the lifecycle reads current only when the record and every install agree. Lifecycle state that is unreadable or points outside the repository stops every command that needs it, and so does state missing where the installed release always writes it, once it entered Git history or when that history cannot be read; Blueprint never rebuilds that history, and an upgrade that finds the state changed underneath it leaves the checkpoint where it was. Missing state that no commit reachable from any ref ever contained is not treated as lost, because the history Git can still show does not prove a lifecycle existed: the repository is dated from provable facts like any adoption that predates lifecycle state, and a 3.2 config shape dates it only in this case, never over lost or unprovable state. That covers a 4.0 adoption whose package Renovate, Dependabot, or `npm update` moved to 4.1 before `upgrade` ran, and, since Git cannot tell the two apart, a lifecycle-aware adoption that never committed the file and then deleted it; commit `.blueprint-lifecycle.json` so a later loss has history to restore from. A package install that stops part-way across several applications resumes on the next run without repeating the installs that landed, while any install mix the recorded upgrade could not have left is refused. `init` records ownership as soon as it writes but establishes the lifecycle checkpoint only when adoption completes, so a failed run, an install deferred by `--no-install`, or an authoring handoff leaves it unestablished until the `init` run that finishes. Every lifecycle state write replaces the file atomically, and completed operations stay readable history after a later release retires them from its supported window, where a newer operation can still supersede them. Re-planning a pending upgrade for a newer release keeps the operations it already completed, so the next run resumes the new plan without repeating them.

`npx blueprint remove` plans the complete de-adoption before changing anything, and `--dry-run` stops at that plan. `init` now records which files Blueprint generated or created, which managed sections it owns, and the exact shared-file edits it made, so removal deletes only proven Blueprint artifacts, strips only managed sections, reverses only recorded edits that are still intact, deletes a Blueprint-owned file such as a migrated `blueprint.config.mjs` instead of restoring it from its recorded edits, keeps alias wiring that application source still imports, and uninstalls `@kekkai/blueprint` last, together with the ESLint packages Blueprint recorded installing that nothing else still uses. A package script that holds neither what Blueprint wrote nor what it replaced, a recorded edit that now appears more than once or records only removed text, broken managed-section markers, and remaining Blueprint wiring stop the removal before any change, each reported once however Git and Node spell the repository root; a recorded edit whose inserted text is gone, or a script back at its original value, counts as already reversed, and a mention of `blueprint.config.mjs` or `@kekkai/blueprint` inside a tool config's comment is not wiring; a shared Agent document is deleted after losing its managed section only when the lifecycle records prove Blueprint created it, and otherwise survives, even empty, with a note to review it; a file Blueprint created and later edited is reversed edit-first and then deleted when it matches what Blueprint created; a shared package stays installed while sibling applications remain adopted; removing part of a repository is refused while an upgrade is pending; repositories adopted before lifecycle records exist lose only provable artifacts and get a report of what could not be proven.

Generated Agent contracts, the packaged agent contract, CLI help, and the English and Traditional Chinese documentation now route "upgrade Blueprint" and "remove Blueprint" requests to these commands.
