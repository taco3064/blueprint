description: Turn a stated direction into one new GitHub issue deliver-ticket can build without re-deriving scope — investigate the current code and history, resolve through discussion every decision the code cannot answer on its own, and land a Goal / Implementation Plan / Acceptance Criteria draft that is true of `main` at the moment it is written. Use when the owner opens with a direction rather than a spec ("we should…", "there's a gap in…", "I want X to do Y"), or when a discussion needs to become a ticket, or when the owner says to start delivery on an issue already filed — this skill dispatches deliver-ticket at it, cold, from the issue's own text. # shape-ticket — one direction, one issue, grounded in what main actually contains

You own the discussion that turns a direction into a **decided** shape. **You do not own how it gets built** — that is [deliver-ticket](../deliver-ticket/SKILL.md)'s, and it starts from the issue you write, not from this conversation. Once the issue is filed, **the shaping is done for that direction — the run is not.** On the owner's word this skill dispatches `deliver-ticket` at that issue and then reports its progress from the GitHub record, per `create-the-ticket.md`'s *The owner's word starts delivery* and this page's own *Progress on any delivery this run reports is read from the record* below. Reopening the same discussion later, or shaping a different direction, is a new invocation — with one narrow exception: correcting a still-open gap in the plan or acceptance criteria of **the issue this run is answerable for — the one it filed, or the one it was told to start delivery on** — even after `deliver-ticket` has started work on it, whether or not a stage has actually landed yet — per [`revise-an-in-flight-ticket.md`](./references/revise-an-in-flight-ticket.md). **A run that filed nothing is still answerable for the issue it was told to start delivery on**: it is the run the delivering session announces to and hears back from, and one barred from correcting that ticket would be left handing a sentence it already knows is wrong to an agent it is watching. That exception never extends to the goal — a goal change is a new direction, not a correction.

**You do not touch the repository.** No edit, no commit, no branch, no PR — and that includes never switching, pulling, merging, or resetting whatever checkout this session happens to be sitting in, even mid-investigation. The one exception is syncing the local read-only ref to `origin/main` — first thing in `inspect-the-repo.md`, again in *Re-sync before you draft* below — which changes nothing tracked. The one artifact you produce is a single GitHub issue — everything else this skill does is investigation and conversation that either becomes a line in that issue or is discarded. **In-flight revision (above) is edited on the issue itself, still never the repository's code.** **Dispatching delivery doesn't loosen any of this either** — the agent this run starts owns the branch, the commits and the PR, and this skill's own hands stay off all three.

**And if a matching issue already exists, you don't create a second one.** This skill's precondition is that no issue covers this direction yet. If the owner points at an existing issue, or `inspect-the-repo.md`'s search turns one up covering the same root cause, **stop before drafting** and report it — its number, its state, and, if its scope still looks unsettled, that settling it is not this run's job. There is no path in this skill from "an issue already exists" to "file a new one anyway": that would produce exactly the duplicate the completion bar below rules out, and editing that other issue in place is not this run's job either — both ends are closed on purpose. (This is a different case from editing the issue *this same run, or an earlier run on this same direction, already filed* — that path exists, narrowly, in `revise-an-in-flight-ticket.md`.) The one way an existing issue legitimately appears in a filed draft is *superseding* it: a closed or withdrawn issue this direction genuinely replaces with a different approach, named in *Related work* the way #364 named #358 and #361. An open issue on the same root cause is never that — it's a stop, not source material, with the one carve-out immediately below.

**A record issue is a source, not a duplicate.** An open issue carrying **no implementation plan, no acceptance criteria and no fingerprint** is a record of a direction, not delivery-ready work on it — so filing one of the pieces it splits into is not a second issue on the same root cause; it is the thing that issue exists for. **What stays a stop is an open issue that *is* delivery-ready on the same root cause.** #378 is the case the rule got wrong: it carried none of the three, said so in its own body, and anticipated being split, and this skill halted on it to ask permission for the obvious. Read the three and the issue answers it — no round-trip. The split's own shape, how many pieces and which of them comes first, is still *One direction can hide several tickets* below and still the owner's; the carve-out settles only whether the record issue is a duplicate.

**deliver-ticket also bounces a ticket back** (its own `start-or-resume.md` names the same seam from the other side), and which recovery applies branches the same way *revise-an-in-flight-ticket.md* does — this line used to say "never editing it while it's still open," full stop, and that stopped being true the moment the exception above existed: a missing or invalid fingerprint, a goal that moved, or a correction that would invalidate a stage `deliver-ticket` already landed is still the owner closing that issue, naming why, and this run superseding it via *Related work*, same as ever. A gap in the plan or acceptance criteria alone, with the goal unchanged and every already-landed stage (zero or more of them) still valid under the fix, is the in-place path instead — the still-open issue is edited, not superseded.

**Everything on this page is always in force.** The depth belonging to one moment lives under [`references/`](./references/) — read the file when its trigger fires, before acting.

## Ask only what the repo cannot answer

Most of what feels like an open question is already decided. `CLAUDE.md` states positions directly (module shape, layering, what counts as an out-of-scope change). `docs/philosophy/` and `docs/guide/` state the product's stances for an adopter. And the code itself states the rest: `missing-layer`'s message is the position on declaring ahead of code, `renderCoverage` is the position on reporting enforcement that is not real — `CLAUDE.md`'s own **"Looking up a stance this project already took"** section is this exact discipline, aimed at the code instead of a conversation. It applies here undiminished: **read what the tool already says out loud before asking whether it says it.**

A direction is *underspecified*, not *unanswerable*, when the repo already implies the missing piece. The discussion budget belongs to the part nothing already answers — not to re-deriving a stance that exists two files away from where you're about to ask about it.

**And a question is not free.** Each one costs a round-trip and a slice of the owner's attention, spent before anything else can move — which is why anything that *feels* consequential gets routed to him regardless of which bucket it is actually in. **So the default is decide-and-state**: settle it, record the basis, and let the owner override if he disagrees. **Escalate only when proceeding under any assumption would be unsafe, or would make the work useless if wrong.** This skill's first run put ten decisions to the owner and at most two of them needed him; `resolve-the-direction.md` carries the bar, the four ways a question gets manufactured — including *A shortfall the ticket's own boundary answers is not an escalation either*, which routes a relayed shortfall back to this same bar — and the floor a reported finding has to clear.

## One direction can hide several tickets

**Investigate before you assume the direction is one ticket.** A direction stated in one sentence sometimes decomposes into two or three capabilities that don't share a root cause and don't need to land together. If that's what you find, **say so and stop** — name the pieces, and let the owner decide the split and the order. Don't file the first piece to make progress, and don't force the whole thing into one issue because splitting felt like more work than it was worth.

The opposite failure is just as real, and it's the one deliver-ticket's own "you do not create tickets" rule exists to prevent: the arrangement it replaced let eighty-five tickets get filed in two days, six of them on a single cause, because nobody looked at the set before filing the next one. **Splitting by every difference you notice is not more careful than not splitting at all — it's the same failure to look at the set, aimed the other way.** Cut by root cause, not by how many things caught your eye.

**One shape-ticket run files at most one issue.** Not a parent and its children, not "the rest tracked separately" — if there is more than one, this run names them and creates none until the owner says which comes first.

## The issue is deliver-ticket's whole briefing

deliver-ticket reads the ticket number, not a summary of this conversation — that's stated in its own SKILL.md, and it means whatever you leave implicit here does not survive the handoff. An implementer with a goal and no edge finds the edge by crossing it; a plan with an unstated assumption gets a different assumption substituted at build time; an acceptance criterion that doesn't name a command gets satisfied by whatever the builder believes is close enough. **Ambiguity you don't resolve here is not deferred — it is reassigned to someone with less context than you have right now.**

**It's also a stricter gate than a briefing.** deliver-ticket's own `start-or-resume.md` refuses to start work on any issue that doesn't carry the fingerprint `create-the-ticket.md` writes below — `<!-- blueprint-shape-ticket:v1 -->` and a `grounded-at` commit that actually resolves — plus the three populated headings the fingerprint accompanies. The fingerprint is what makes this a check on whether the shape-ticket *process* ran, not just whether the output happens to have the right *shape*: three headings with the right names are something anyone can type by hand without running anything at all. It's a process marker, not a security proof — see *Fingerprint* in `create-the-ticket.md` for that boundary — but for a solo, non-adversarial pipeline it's exactly the bar this gate needs. An issue this skill files is deliver-ticket's only accepted entry point, not merely its preferred one; getting the fingerprint right here is what lets the other skill trust the issue without re-deriving what produced it.

That is why the completion bar below is strict, and why it's checked before the draft is shown, not after:

- The goal has no open product decision left in it.
- The implementation plan is built on the module and layer that CLAUDE.md already says owns this, names the primitives already in the repo instead of inventing new ones, and is true of the commit it was read against.
- Every plan stage is independently landable and verifiable — the same bar `deliver-a-stage.md` holds a commit to, applied one level up.
- Every acceptance criterion names a command, an output, or an artifact — not "works correctly" — and maps back to a goal clause or a plan stage. An orphan criterion or an unproven goal clause is a hole.
- Anything adjacent that this issue does not cover is named as out of scope, not left for the reader to guess.
- Nothing in the draft silently duplicates another issue's scope. An open issue already covering this root cause means the run stopped before a draft ever existed (see *And if a matching issue already exists, you don't create a second one* on this page, and its carve-out *A record issue is a source, not a duplicate* — a record issue is a source and doesn't trigger this stop); a closed or withdrawn one this direction genuinely supersedes is named in *Related work*, not silently repeated.

## Discussion is not a form

**One blocking decision at a time.** Not a checklist fired at the owner in one message — each question waits for its answer before the next one is asked, because an early answer routinely changes what the later questions even are.

Every question carries, in this order: the current state and the evidence for it, the real options with their actual consequences (not which is less work to build), and a recommendation with its reasoning. A question with two options that behave identically isn't a question — it's a coin flip dressed as one, and it costs the owner's attention for nothing.

**Keep a running decision log for the length of the conversation** — what's confirmed, what was considered and rejected and why, which constraints must hold, and which of those came from the owner versus were derived by you from the repo. Don't re-ask a settled decision. If something surfaces later that contradicts one, that contradiction goes back to the owner explicitly — it is not quietly reconciled in your own head, because a silent reconciliation is a second, unreviewed decision wearing the first one's name.

## The run reports its own bill

**A run reports three numbers about itself, together or not at all — whenever the run ends, however it ends.** Handing the issue over is one ending — **a stopping point rather than the run's last, now that a dispatch can follow it**; so is the end of an in-flight revision pass; so is a stop that files nothing — a duplicate found at pre-flight, or a direction that turned out to be more than one ticket. **That files-nothing exit is the cheapest one to reach and the one nobody counts**, and it is reached after the whole discussion has already been paid for. **Two more endings arrived with the dispatch.** A run whose whole job was *"start delivery on #N"* ends when the agent is dispatched and its name reported — it shaped nothing and filed nothing, and it still reports. **And the last ending is the one handing the issue over stopped being: the delivery this run dispatched reaching its own end**, with everything this run reported off that record in between inside the bill rather than beside it. The three numbers:

- **Decisions put to the owner**, each with its basis. A question the issue text, the repo, or a stated default already answered is a defect of this run rather than a data point. The number to beat is this skill's first run: ten, of which two were justified.
- **Requirement movements this run authored after filing**, per stage and in total, **counted from the record and not from memory, and in one unit: the `requirement movement count` `deliver-ticket` keeps on each stage's review-state comment.** A revision pass is not that unit and does not convert into one — a pass can move no requirement at all, and #379 ran fifteen of them — so the pass count is a cost and belongs to the third number. **The baseline is read off the same field the unit is:** `deliver-a-stage.md` writes it *"0 or 1"*, because a second movement on one stage is meant to stop that stage, and #379's stage 9 stood at `requirement movement count: 3` — the brake reached and then passed twice, each pass with its reason written into the same comment. **Anything past 1 on a single stage is the number to beat**, and it is legible without reconciling two units.
- **What the run cost** — elapsed time, comments, revision passes, issues opened, and what actually shipped. #379's was two days, 60 comments, 15 revision passes, 11 issues, and 24 commits for a fix that is one guard on one branch of one function, filed as one stage and planned to twenty.

**Where an ending cannot answer a number, the run states the reading rather than leaving the number out.** **On an exit that files nothing, the second number is zero and *what shipped* reads *nothing*** — a movement needs an issue to move. Zero is a reading, not a reason to skip the report: that exit is the one where every escalation was already spent and nothing came back for it. **At the filing ending nothing has shipped yet**, so *what shipped* reads *filed, not delivered* — the third number there is what the shaping cost, and a run that borrows a claim from a delivery that has not started has reported someone else's number as its own. **A cold dispatch answers all three and mostly with zeroes**: nothing was put to the owner, nothing had moved yet, and the cost is the dispatch. **What the delivery goes on to cost is read off the record at the delivery's own ending**, which is why that ending is one of them.

**Two of the three is not a measurement.** Escalations and movements are one bill with two ends: a run reporting zero questions and more movements than #379 has not improved, it has moved the cost onto the delivering session, where it arrives as voided reviews and stopped stages. **And a run that decides better and costs more has not improved either** — which is the third number's whole job.

## Re-sync before you draft

`inspect-the-repo.md`'s *Ground the investigation before it starts* fetches `origin/main` and records its SHA before the first fact that will shape the plan is read — everything from there on, including every product decision `resolve-the-direction.md` settles, is read against that commit, never against whatever the session's own checkout happens to be on. This repo moves same-day, though, so before writing the draft that grounding needs a second, identical sync: `git fetch origin`, read-only, changing no tracked file and moving no branch — never `git pull`, `git checkout`, `git merge`, or `git reset`, which is exactly what *you do not touch the repository* rules out, applied to this skill's own investigation instead of to the code.

**Diff the two SHAs instead of re-reading everything.** `git diff <grounding-sha> origin/main` names exactly which facts moved since grounding; an empty diff on the paths this direction touches means the investigation still holds, and a non-empty one says precisely what to re-check rather than triggering a second full pass. `create-the-ticket.md`'s pre-flight covers this from the drafting side.

## Progress on any delivery this run reports is read from the record

Dispatch itself is `create-the-ticket.md`'s *The owner's word starts delivery* — but **none of this is scoped to a delivery this run dispatched.** It binds whenever this run reports on, or watches, a delivery at all, because the owner has one conversation about a ticket and it is this one. Every incident below is from **#379's delivery, which no shape-ticket run dispatched**: it was watched from a peer session, and that reader is exactly the one this discipline is for. Only re-dispatching a dead agent needs the delivery to be this run's own.

- **A progress report reads the GitHub record, never the agent's last message.** Branch commits and the issue's stage, review-state and delivery comments are the authority; a subagent's report is a convenience. **Name the source in the report**, so *"no new commits on the branch since `<sha>`"* is a fact rather than an inference from silence. Silence is the inference this skill actually made about #379's delivery and had corrected, recorded on #385: idle meant a dispatched sub-agent was in flight, not that anything had stopped.
- **A delivery agent *this run dispatched* that dies is re-dispatched at the same issue, and nothing is rebuilt** — the one clause here that needs an agent of this run's. `deliver-ticket`'s `start-or-resume.md` already reconstructs the whole state from the record — the round count, the protocol retry count and its reasons, the requirement movement count, the staged diff's hash, and *"pass one recorded, part two unsent"* as its own state — and says why in terms: **"The budget continues from that number; it does not reset because a new session started"**, which is the whole reason the count is on the ticket. It is repeated here so that a run meeting a dead agent doesn't invent a worse answer than the one already written.
- **Before arming a watch on a delivery, name the states it cannot tell apart — and if "still working" is one of them, it is not a watch, it is a reminder to go and look.** The instrument watching #379's delivery failed that twice, both misfires recorded on #385: a watch on commits, comments and the PR fired *"stalled"* while files were being edited, and adding file-touches to it fired *"stalled"* while a dispatched reviewer was reading and touching nothing. **Both misfires were on a live, healthy session**, and acting on either would have interrupted it. The gate state is what closes the gap: a stage whose review-state comment reads `dispatched` explains a quiet tree, so the alarm carries that rather than making the reader go and fetch it.
- **And a watch is retuned against its accumulated direction, never against the last complaint alone.** That same watch was rebuilt three times for crying wolf, and the fourth version suppressed a real ninety-minute stall by reading a stale `dispatched` out of a closed stage's running log. **Each rebuild was a correct local response to a real false alarm; the three together tuned the instrument to miss** — *"A tuning history is a design decision nobody makes"*, and the same shape as #379's stage 9: *"Three fix rounds have each normalised one spelling and each produced a new instance of the same class"*. **So the direction of a miss is part of the check: one that fails toward noise gets read and corrected, one that fails toward silence cannot be read at all.** Before retuning, ask which way the last three moves took it.

## Every comment names its author, a retraction reaches back, and a citation waits for its target

**The ticket is a shared record and GitHub shows one author for all of it.** This skill and `deliver-ticket` push through the same account, so #379's thirty-eight comments — two sessions, three roles — read as one name throughout, and nothing on the page says which role wrote any of them. **A convention half the writers apply is not a convention**, because its absence stops meaning anything: the rules here are one convention held in two places, stated on this page and in `deliver-ticket`'s own `SKILL.md`, under *The ticket is the record, not just the target*, and they move together or not at all. That is the whole of what the owner lifted the single-skill boundary for — what the other skill's comments carry, and nothing else about it.

- **Every comment this run posts names its role in its first rendered line, without the comment being opened** — a revision pass and a ruling alike, and anything else this run leaves on an issue. The role word is one of four — **shaper**, **implementer**, **reviewer**, **owner** — and this run writes `shaper` on all of its own. **The property binds, not a form**: a heading word, a prefix, a bracketed tag each satisfy it; a label that appears only once the comment is expanded does not, because the cost is paid by whoever is scanning a stream of thirty. **The four words are fixed, and fixed in both skills together** — one side of the seam spelling a role differently is a filter that silently drops half the stream, the same kind of decision as `v1`, which is made in both `SKILL.md`s or in neither. The measured cost of carrying none: the monitor watching #379's delivery reported this skill's own revisions back to it as delivery events, twice, with the comment's prose as the only filter available.
- **The HTML markers stay, and the issue body is not a comment.** `deliver-ticket`'s stage-review marker addresses a session coming back, and GitHub renders it as nothing; the role word addresses a person and is the first line that renders. Neither substitutes for the other, so neither replaces the other. And the body's first two lines are `create-the-ticket.md`'s fingerprint with nothing above them — the status section that would otherwise arrive here is already ruled out by `revise-an-in-flight-ticket.md`'s *Say what's landed as of this revision, in the comment — never as a maintained section of the issue body*, on a reason nothing since has disturbed: a status line in the body is stale by construction, since only this run edits the body and only delivery lands stages, while a label describes the comment it sits on and cannot go stale that way.
- **A decision this run wrote that is later withdrawn, superseded or overtaken is marked at the decision itself, not only at what replaced it.** All three modes, not only the one the run performs as an act of its own: a ruling it retracts, a claim an earlier revision pass made that a later pass replaces — the commonest of the three on this side, since `revise-an-in-flight-ticket.md` keeps each pass's prior wording in that pass's comment and #379 ran fifteen of them — and a decision the owner overturns. **Edit the original comment**: say which of the three happened, where the role word already is, and point at what replaced it — **and leave the rest of its body intact, because the reasoning that was wrong is what stops it being re-derived.** **Find that comment through `gh api`, never `--edit-last`, which targets the latest comment on the issue and something will have landed since** — the same mechanic `deliver-ticket`'s *The ticket is the record, not just the target* names, and the reason it is repeated here is that this side writes fewer comments and edits older ones: the pass being corrected is usually several passes back. *Repo facts* on this page names `gh issue edit --body-file`, which is the issue **body** and never a comment. The case is `resolve-the-direction.md`'s own: the stage-3 fix-budget ruling was refused with evidence and withdrawn two minutes later in a separate comment, which said *"a withdrawn ruling that leaves no trace is a ruling somebody re-derives"* and then left no trace on the thing it withdrew. A reader who stops at the ruling, or meets the stream in order, acts on a decision that no longer stands. **Deleting it was never the remedy either** — a retracted decision that has vanished is one somebody derives again from scratch.
- **A cross-reference is written after its target exists, never before.** A citation **asserts that the thing it points at is there**, so a URL, a comment number or a file path written ahead of the write it names is false at the exact moment it is most likely to be read, which is while the reader is following it. **An exit code reports that a command ran; a pipeline's does not report that it finished; a diff reports that something changed, not that the intended thing did; and a citation reports nothing at all — it asserts.** The first three are checked by reading the changed line back. **The fourth has nothing to read back, and is checked by ordering: create, then cite.** The instances are the delivering session's and it disclosed both — a review-state comment carrying an escalation's URL before the escalation was posted, the number wrong and corrected after, and a dispatch naming a commit-message path before the message existed. **This run has no instance and the rule binds it anyway**: it writes more cross-references than delivery does, and it has been lucky rather than careful. It is also what makes the withdrawal rule executable — post the replacement, then edit the original to point at it.

## Repo facts

- File with `gh issue create` or the GitHub MCP tool, whichever the session has. Title and body are English, matching every existing issue in this repo — the title states the outcome or a directive with its reason (`"The gates run at error, and the code meets them"`, `"Add an eslint 10 CI leg — the tool installs it unpinned and nothing tests it"`), never ticket-speak, never a filename standing in for a capability. Revise the same way, with `gh issue edit --body-file` — never `--title`, since a title change on a filed issue is exactly the kind of scope drift `revise-an-in-flight-ticket.md` rules out.
- **Use only labels that already exist** (`gh label list`); don't create one for this issue. Don't set an assignee, milestone, or parent issue unless the owner explicitly asks.
- `CLAUDE.md` and `.claude/docs/` hold the conventions the plan must not contradict. Read the doc when its trigger fires; don't substitute first-principles reasoning for what it says.
- One issue per run. No sub-issues, no follow-ups, no "tracked separately" issue filed alongside it — if the direction needs more than one, say so per *One direction can hide several tickets* above and stop.
