# Delivering a stage

**Trigger:** you are about to dispatch a sub-agent, about to dispatch or answer a reviewer, about to commit, or you have just committed and owe the ticket a comment.

## What a stage is

**A slice of the ticket that stands on its own: the repo is green and releasable when it lands, whether or not any later stage ever does.** Not a checkpoint of convenience, not "I stopped here because it was late".

**Green is not the same as honest.** A stage can leave every gate passing and still misrepresent the state — a debt ledger carrying rows you already know a later stage removes, a suppression standing in for work simply not done yet. That is still a legitimate stage, and the comment is where the distinction has to live: which rows are debt, and which are only recorded until the commit that closes them. The gate cannot carry that difference and the ledger file has nowhere to put it.

If a slice can only be verified together with the next one, it is not a stage — it is half of one, and committing it splits a single verifiable change into two comments that each prove nothing.

Cut stages by **what becomes true**, not by which files you happened to open. *"The schema accepts the new field and rejects three ways to get it wrong"* is a stage; *"edited `defineBlueprint.ts`"* is not.

**A ticket that only makes sense as one commit is one stage.** Do not manufacture stages to have something to report — a single commit with a single honest comment is a complete delivery.

## Dispatching it

**A fresh sub-agent per stage, given a Stage Packet — not the ticket number and an instruction to go read it.** Handing over the number and trusting a sub-agent to read "just the relevant part" doesn't bound anything: `gh issue view` returns the whole body and every comment regardless of what it was told to focus on, and a sub-agent that fetches the issue itself has paid the full ticket's cost no matter how narrowly it was asked to read. The packet is what actually shrinks the input; an instruction alone only shrinks the attention.

**Build the packet by extracting verbatim, not by summarizing.** The issue stays the single source of truth; the packet is a projection of it, not a second account of it — copy the exact text spans, don't restate them, the same discipline as *hand over the number, not your summary* applied to the parts instead of the whole. It carries:

- The issue's `## Goal`, verbatim.
- The one stage's own text from the Implementation Plan, verbatim, and its corresponding acceptance criteria, verbatim.
- Whatever the plan states must not change (the global invariants), verbatim.
- Shape-ticket's cited references — the module, the primitives, the consumers, the docs pages named as required reading.
- The commits of stages already landed, so it builds on top of real code rather than re-deriving it.
- Any shortfall still open that affects this stage.
- The issue's number and URL, for traceability — not as an invitation to fetch it.
- The instruction to read `CLAUDE.md` and every `.claude/docs/` page whose trigger fires for this change.

**Tell the sub-agent not to load the full issue or its comment thread — the packet is what it works from.** The one exception is the packet turning out self-contradictory or missing something the stage actually needs; that's reported back as a shortfall or a question, not a license to go fetch the rest quietly and reconcile it itself.

**What the packet excludes**: shape-ticket's discussion history, the full text of options the discussion rejected, every closed shortfall's full history, other stages' implementation detail, or any prior agent's reasoning. None of that changes what this stage has to make true, and carrying it anyway is exactly the cost this packet exists to cut.

Tell it what the stage is in terms of **what must become true**, and tell it the boundary in the same breath — what this stage does *not* cover, and that anything it notices outside the stage is reported rather than fixed. An implementer given a goal and no edge will find the edge by crossing it.

**Ask it for what you need to write the comment**, since it has it and you do not: the commands it ran and their output, which of its claims it measured and which it reasoned, and anything it noticed and did not act on. **Name the file it writes that report to, and tell it to write the file before it returns the summary** — what it is asked for does not change, only where it puts it, and *A dispatched agent's report is written before it is returned* is the rule and the reason.

### A dispatched agent's report is written before it is returned

**A report that exists only in the message carrying it dies with whoever was going to receive it.** #385's own delivery has one instance on each side of the seam. A reviewer raised a REQUIRED and was killed between part one and part two: its handback never reached the dispatcher, its replacement's independent pass one did not find the same thing, and a completion-test reader found it again two stages later — one finding, one wasted reader cycle, and every decision in between taken on the premise that it did not exist. An implementer wrote the closing commit's six files and reported to a dispatching session that then died: the report exists nowhere, searched for and absent and not on the ticket either, so the review that followed audited no claim by the party under review because there was none left to audit. **A report and a handback die the same death, and only one of them had a rule.** **Receipt is a precondition of durability, and the party that wrote the report is the one least able to guarantee it.**

**So every agent this page dispatches writes its report to a file before it returns it, and hands back the path with it.** Both kinds, because both kinds exist here and the pair is the whole of it: the implementer's report, and `review-stage`'s pass-one handback and its final report. **The dispatch names the file, the dispatched agent creates it, and you read the file rather than depending on the message arriving.** A third kind of handback is a new ticket, not a wider reading of this one.

- **One directory per stage, outside the worktree**: `deliver-ticket-<n>-<stage-slug>`, the issue number and the stage slug, directly under the temp root a bare `mktemp -d` creates in. **The slug is formed from the ticket and the tree, not read off the review-state marker** — *The review state goes on the ticket at the dispatch, not at the first BLOCKED* is where the formation rule is written, and the marker carries that slug rather than being where it comes from, which is what lets this directory be named while the comment it would otherwise be read from does not exist yet. **Derived rather than invented**, so a dispatcher holding the ticket and the tree can name the whole path rather than merely recognise it once somebody else has — **and it holds both wherever the derivation is needed**, since the window this exists for is a staged tree no review has run on yet. **Not the session's scratchpad either**, whose name the session that replaces yours does not share. **Its root, never the command itself**: a `mktemp -d` is the wrong instrument here for the one reason it is the right one for a parked patch — its name is random, and nobody who did not run it can name it again. **Never inside the worktree**, which would add an untracked file to the very diff under review.
- **Every dispatch names its own file in that directory and never reuses a name an earlier dispatch used.** A replacement reviewer writing over its predecessor's handback destroys the one copy this arrangement exists to keep.
- **Record the path on the review-state comment at the dispatch that names it**, per *The review state goes on the ticket at the dispatch, not at the first BLOCKED*. **The implementer's dispatch runs before that comment exists**, so its path goes on the comment the moment the comment does — and the derived directory is what carries it until then, which is the whole reason the directory is derived rather than invented.
- **A dispatcher arriving fresh at a staged tree opens that directory before it re-enters the gate.** `start-or-resume.md` sends a staged, uncommitted worktree that no review-state comment names back through part one from the start, and **that is the exact window the implementer-side incident this section opens with happened in**: the implementer had written and returned, the dispatching session died before any comment existed, and there was nothing on the ticket for a path to have been recorded on. **The directory is derivable from the issue number and the stage slug, so read it rather than concluding from an empty comment stream that no report was ever written** — a report sitting on disk and a report nobody wrote look identical from the inside, and only one of them can be recovered. What is there is the implementer's report for the diff that is already staged: it is what part two's claim audit is run against, and what *The comment, one per commit*'s *what you ran* and *which claims are measured and which are reasoned* are written from. **Record its path on the review-state comment the moment you create one**, per *Record the path on the review-state comment at the dispatch that names it*, so the next session recovers it instead of deriving it again. **And if the directory is empty, say so where that path would have gone rather than leaving the silence to be read as a report that was made** — the review that follows then audits no claim by the party under review, which is a cost to record and not a gap to fill by reconstructing a report nobody wrote.
- **A recovered handback enters part two, never a replacement's part one.** It is somebody else's conclusion whoever recovers it, so it arrives where every account written by another hand already arrives — `write-the-verdict.md`'s *Part two may also carry a previous reviewer's findings*. Recovering it is what makes the finding survive its author; handing it to a fresh pass one is the anchoring the two parts exist to prevent.
- **The file is machine-local and the ticket is still the record.** It survives a killed agent and a killed session, which is the incident; it does not survive a different machine. **The review-state comment stays the record of record** — this makes a handback recoverable, it does not make the file the authority.

## Before you commit

**Verify what came back rather than accepting it.** *"Done, tests pass"* is the implementer reporting confidence; it is not evidence and it is not yours until you have run it. Re-run the layer that matters, read the artifact if the stage touched one, and read the diff — **not for style, for scope**: a change wider than the stage is the most common thing a dispatch returns, and it is invisible in a summary.

**When the diff is too large to read, say which instrument read it instead.** A mechanical sweep across sixty files is not something you walk line by line, and reporting it as reviewed when you ran gates over it is the exact failure this page is about. Name what actually carried the check — the suite, a byte baseline, a rendered artifact. An unread diff with its instrument stated is honest; an unread diff called verified is not. **Whoever actually reads it is *The review gate* below** — stating your instrument is how you report the limits of your own pass, not a second reader you dispatch instead of that one.

If what came back is wrong or incomplete, **that is not a shortfall** — a shortfall is something true about the repo. It is an unfinished stage: dispatch again with what was missing, and do not commit in between.

- **Run the layer that could catch this**, not the cheapest one. `.claude/docs/verification-layers.md` says which is which. A unit test proves the logic; it does not prove the emitted artifact says anything.
- **If the change touches emitted prose, render it.** Enumerate the conditional branches from the code first, render one file per combination, and read them. An empty diff from a branch you never rendered looks exactly like an empty diff from a branch that did not change.
- **A fact this commit states on more than one surface is read on all of them, in the same pass.** One commit routinely writes documents that outlive it and are read by different people: a **doc comment on an exported symbol**, which becomes the API reference; the **emitted prose**; the **commit message**; and — on the one commit per ticket that carries it, per `finish-the-ticket.md` — the **changeset**, which becomes the release note verbatim. **No gate compares them, and the fix to one of them is what usually breaks the next** — #371's stage 5 blocked twice this way, the second time because the doc comment repaired in the previous round attached a ruled exception to exactly the claim the changeset in the same commit had just been corrected to deny. **So enumerate the surfaces before reading the sentence on any of them.** A sweep that stops at the first hit returns something shape-identical to a sweep that found nothing else, and this stage's sweeps were short by six twice before one was written as a question — *for every hit, does this sentence's subject actually change?* — instead of as a list.
- **Never bypass the commit gate.** Not `--no-verify`, not `-n`, not `HUSKY=0`. If it stops you, the thing it stopped is the thing to fix.
- **And a gate that stops you may be saying your stage *order* is wrong, not your stage.** A hook that autofixes on the way in can produce violations no ledger holds, so the first commit touching a governed file fails on work belonging to a stage you have not run yet. Park the finished stage as a patch, land the one the gate named, re-apply. That is the gate working, and the order it forces is usually the honest one. **The review follows the commits, not your drafting order**: whichever stage lands next is the one reviewed next, and the parked one is reviewed when it is re-applied — a verdict on a patch that is not the tree is a verdict on nothing.

## The review gate

**Verify it yourself first, then hand it to a reviewer that has seen none of this.** Your own check above is a filter, not the review — a stage that does not lint, type-check or build has no business costing a review round. What it cannot be is the review itself: you chose the stage and wrote the packet, so *"was this the right thing to have asked for"* is not a question you can answer about your own instruction. `SKILL.md`'s *A stage is not yours to pass* is the standing rule; this is how it runs.

**Dispatch it in the background, and let nothing advance while it runs.** Not the next stage, not a commit, not a comment. The next stage builds on this code — starting it before the verdict means a BLOCKED arrives on top of work that already assumed a PASS, and untangling that costs more than the wait ever did.

**One reviewer per stage, continued across its parts and its rounds** — fresh per stage exactly as the implementer is, and continued within one, because re-verifying a finding means re-running the reproduction whoever wrote it holds. **That trade is deliberate and it is not free**: a reviewer carried across rounds accumulates its own investment in the findings it filed. `review-stage`'s re-review rules are what answer that — a PASS at the end has to rest on the fix diff read as a change in its own right, not on three earlier findings having disappeared.

**Continuity is the ideal path, not a fact you can assert.** A sub-agent does not outlive the session that spawned it, and writing *"the same reviewer"* in a rule does not make a fresh one the same. So the downgrade is defined rather than improvised:

- **The original is still reachable** → continue it, which is the case above.
- **It is gone** → dispatch a new one **with part one only**: the current requirement text and the current diff, and nothing about what its predecessor concluded. It does its own pass one first.
- **Then part two carries the prior findings, the fix reports and the round count.** That needs no new machinery — part two is already where every account written by somebody else arrives — only the discipline not to shortcut it, and a copy of the predecessor's handback that outlived it. **A reviewer killed before it could return one still wrote one**, at the path its dispatch named, and recovering it there is what keeps its findings in this loop rather than in a completion-test reader's two stages later — *A dispatched agent's report is written before it is returned*.
- **Rounds already spent stay spent.** A new reviewer is not a new budget; the count lives on the ticket precisely so a change of reviewer cannot reset it.

**Handing a replacement its predecessor's findings on arrival is exactly the anchoring the two-part packet exists to prevent** — and it is more tempting here than anywhere else, because old findings feel like context rather than like someone else's conclusions.

### The frontier is widest on the first pass and narrows after

**A ticket is written before the code is read, so the first review is where its scope is allowed to be wrong.** A reviewer that finds a second file reaching the same parser has found something the ticket meant to cover and failed to name, and pulling it in is the review doing its job, not scope creep. **Say so in the handback and let the frontier widen once.**

**What makes that expansion bounded rather than a second ticket is a named membership instrument** — either a command that lists every member of the class, or **a question that can be put to every candidate in a corpus you can enumerate.** Both are real, and the second is not the weaker one: this page's own four-surface sweep is that kind, and it records that the list form was short by six twice before the question form worked. What bounds nothing is *"it feels related"* — that is an association, and an association goes under *Observations outside this purpose* in [`finish-the-ticket.md`](./finish-the-ticket.md). **The strongest form is two instruments built on different vocabularies returning the same set**, because agreement between checks that could not have made the same mistake is worth more than either one's confidence.

**After that pass the frontier is frozen — which bounds what a re-review may investigate, never how completely it reads.** `review-stage`'s *Re-reviewing a fixed tree* still governs the round unchanged: its six questions in order, then the fix diff read completely as a change in its own right, and **a finding seen there for the first time is still a finding.** What the freeze bans is the other thing — **re-deriving the whole repository every round, and opening an axis the first pass did not.** A reviewer that rebuilds the picture each round will keep finding things, because there is always more to find, and **a stage that ends only when a reader runs out of ideas does not end.** The fix budget never bounded that: it bounds how many times the code may fail, not how many times the question may change.

**So the round is spent on four things**, reached through that procedure rather than instead of it:

- Is the original finding actually gone — re-run, not read?
- Did every sibling the membership instrument names get the same repair?
- Did the fix regress anything already passed?
- Do the changed lines still satisfy the invariants the packet froze?

**One thing reopens the frontier: the fix itself widening the surface.** It adds public behavior, changes a dependency direction, introduces a new parser or a new authority, or puts a consumer on the execution path that was not on it before. **Those four are the whole list**, and the surface they reopen is bounded by the same membership instrument the first pass had to name — never by proximity to the change. **A widening the fix earned is recorded the way the freeze is already read**: the fix introduced a new value on an axis, so the row is added, and *Reading the verdict*'s extend-only check accepts it. **There is no second way to widen legitimately** — one that added no row would leave `Axes in play` byte-identical between the handback and the final report, and the audit blind at the point it was built to see.

**Stage first, then run the gate's own fixer, then stage again.** `lint-staged` runs *on staged files* — that is what it is — so "run the fixer before staging" is not an instruction that can be executed, and rebuilding an equivalent by hand out of its config runs a different program than the hook does. **A tree that has not been through the gate's fixer is not the tree that will land**, so the order is:

1. **`git add -A`.** One command then shows the whole change (`git diff --cached`), which a plain `git diff` does not — a file the stage added and never staged is invisible in a diff, and that is exactly where a stray fixture or a half-written module hides.
2. **`npx lint-staged`** — the gate's own fixer, on the tree it will actually see, rather than a reconstruction of it. **If it fails, the stage fails here instead of after a review has been spent on it**, which is the same filter as *verify it yourself first*.
3. **`git add -A` again**, for anything the fixer rewrote and did not itself re-stage.
4. **`git status --porcelain`** — nothing should be left unstaged. If something is, find out what wrote it before going further.
5. **`git diff --cached | git hash-object --stdin`** — the **code hash**, recorded now.

Then the identity to check the review against:

- The code hash and `git status --porcelain`, recorded **before** the dispatch and again when the report lands.
- **If either moved, the review is void.** Discard the verdict whatever it said, find what wrote to the tree, and dispatch again. A verdict on a tree that no longer exists is worse than no verdict, because it reads exactly like a real one.

### Hash the requirement, not only the diff

**Code that has not changed does not mean the requirement it has to satisfy has not changed.** A reviewer can be mid-pass while `shape-ticket` revises the issue body, the owner adds a decision, an acceptance criterion moves, or a revision comment is updated — and **the code hash is identical through every one of those**, so a PASS earned against the old requirement is indistinguishable from one earned against the new.

So take a **requirement hash** over the authority half of the packet: the Goal, this stage's plan text, its acceptance criteria, the invariants, the owner's decision with its source, and every revision comment's URL, timestamp and body — the exact text you handed over, hashed the same way (`git hash-object --stdin`).

**Re-read those from the source when the verdict lands, before the commit, and compare.** A difference means the verdict was earned against a requirement that no longer exists: that is `VOID` — back to part one with the current text — **and it consumes neither budget**, because nothing about the work or the loop was wrong; the question changed. **A second movement on the same stage stops instead of restarting — so record the first one before you restart**: the `requirement movement count` and the hash it moved to, on the review-state comment. The current hash cannot carry this by itself, because after the restart it holds the *new* value, and a session arriving fresh cannot tell that from a requirement that never moved at all. (*The protocol's own budget* below.) Re-reading the issue is yours to do; the reviewer is the one forbidden from fetching it.

### The Review Packet, in two parts

**Part one, with the dispatch.** Verbatim extracts, the same discipline as the Stage Packet — a projection of what is already written, never a second account of it:

- **The owner's latest decision** on anything this stage turns on, quoted as the owner stated it. That is rank one of `review-stage`'s authority order, and the packet is the only place a reviewer can get it.
- The issue's `## Goal`, this stage's own plan text, its acceptance criteria, and the invariants — **current**, including any in-flight revision, not as first filed.
- **Every revision comment that amended this stage's plan or criteria, verbatim.** `shape-ticket`'s `revise-an-in-flight-ticket.md` **overwrites the issue body on each pass**, so that comment is the only place the prior wording survives — and it is also the only record of which already-landed stage the revision leaves valid, which is what makes "judged by the criteria that stood at the time" reconstructable at all. **A reviewer reading only the current body cannot tell a criterion that always said this from one revised yesterday, and cannot tell which version a landed stage was judged against.** Extract those comments; do not hand over the thread they sit in.
- **Provenance on both of the above**: the comment URL, the author, and the timestamp. *"The owner decided X"* with no source is unfalsifiable as **latest** — which is the one property rank one is ranked for — and a reviewer that cannot date a decision cannot tell it from one that was superseded an hour later.
- Shape-ticket's cited references, and anything the owner has already ruled out of scope on this ticket.
- The base SHA, the worktree path, and both hashes you just recorded — the code hash and the requirement hash.
- **The path this dispatch names for the reviewer's pass-one handback and its final report**, per *A dispatched agent's report is written before it is returned*. `review-stage` writes each one there before it returns it and hands the path back with the verdict line; you record the path on the review-state comment at this dispatch, and you read the report from the file.
- **The frontier**, in the terms *The frontier is widest on the first pass and narrows after* sets: on a first dispatch, that it may widen once under a named membership instrument and must say so in the handback; **on every re-review dispatch, that it is frozen, what the four things the round is spent on are, and that the fix diff is still read completely.** This bullet is what arms that section. **The rule binds the reviewer, and the reviewer never reads this file** — its own reference table names only its three pages, and *Reading the verdict* forbids you to grade its scope afterwards, so a rule not carried here is a rule declared and unarmed.
- The instruction to load `review-stage`, and to read `CLAUDE.md` plus every `.claude/docs/` page whose trigger fires for this change.

**What part one withholds is the whole point of the gate**: the implementer's report, its command output, its reasoning, its self-assessment, **your own verification results**, any earlier stage's reviewer findings, and the issue's comment thread — which is where all of that is written down. Tell it not to fetch the issue, for the same mechanical reason the implementer is told: `gh issue view` returns every comment regardless of what it was asked to focus on.

**Part two, after its first pass comes back — and not until that pass is complete.** The handback has a defined shape (`write-the-verdict.md`): `Claimed scope`, `Axes in play`, `Dimensions crossed` and `Verified` filled in, `Claim audit` empty, and `pass one — not yet computed` where the verdict goes. **Check it before part two leaves, because once part two has left there is no longer any such thing as an uncontaminated first pass.** The freeze those blocks are under is a claim about *when* they were written, and this is the only moment anything can still verify it: a final report with every block filled in is indistinguishable from one whose axes were read off the implementer's report, and checking at the end finds the harm rather than preventing it.

**An incomplete handback goes back as a first pass, not as a missing field.** Not *"add the axes"* — re-run pass one and return the whole handback. The reviewer still holds its packet and has still seen nothing of the report, so redoing it is uncontaminated and asking only for the heading is asking only for a heading. **No fix round**, and it increments the `protocol` count as a `shape` retry — *The protocol's own budget* below.

**Then copy the handback's four pass-one blocks into the review-state comment, verbatim, before part two goes out.** That copy is what the final report gets compared against — without it the freeze is unverifiable, and a session dying between the parts leaves the reviewer's own handback file as the last surviving copy of what was written before the report arrived. **That file is a recovery, not a record**: it is machine-local, the ticket is where the blocks have to end up, and the copy is what a dispatcher on any other machine reads.

**Only then do you send** the implementer's report and the draft commit message, verbatim, for the claim audit. **Sending them with part one collapses two passes into one anchored pass** — the sequence is what makes the independence mechanical instead of a promise. Send it to the same reviewer, which holds its own pass-one findings; a reviewer that died between the parts is a re-dispatch from part one, never a shortcut into part two. **Recovering the dead reviewer's handback from its file does not change that** — what it holds is somebody else's conclusion now, so it rides in the replacement's part two with every other account written by another hand, and the replacement's own pass one is still its own.

### Reading the verdict

**Every verdict updates the review-state comment before you act on it** — that is what makes the next step recoverable if this session ends between the two. **And the report you update it from is the file at the path this dispatch named, not the message that carried it** — a message that never arrived and a file that is there is a report to read, not a round to re-run (*A dispatched agent's report is written before it is returned*).

**Then read the report's shape before its verdict word.** A PASS is an assertion *about the report's own blocks*, and branching straight to the commit is what makes `review-stage`'s *PASS asserts…* advice rather than a gate. **Two different things can be wrong here and they take different remedies, because one of them cannot be fixed by asking.**

**First — do the pass-one blocks still match the copy you recorded?** `Claimed scope`, `Axes in play`, `Dimensions crossed` and `Verified`, against the review-state comment. **Extend-only**: a crossing added because the fix introduced a new axis value is legitimate; a scope reworded, an axis dropped, or a pair appearing for the first time now is not. **A difference here is `VOID`, and it does not go back to the same reviewer** — whatever produced it was produced with the implementer's report in hand, so that reviewer no longer has a first pass to re-run. Dispatch a fresh one, part one only, per *Continuity is the ideal path* above. This is the case `write-the-verdict.md` means by *do not answer a `VOID` by adding the heading*: at this point there is no honest way to add it.

**Second — is `Claim audit` complete**, placing every claim from the report you sent in part two? That block is pass-two output and part two has now happened, so **missing here means missing, not falsified**: send it back for that one block, to the same reviewer, which still holds both passes. It is the only block a re-dispatch can honestly repair.

**Neither consumes a fix round** — the work is not what failed and the tree never moved. And **you are checking that the artifacts exist and did not move, never grading them.** A dispatcher that starts deciding whether a crossing was the *right* crossing, or a scope drawn correctly, has become the second reviewer this gate exists to not be — and it would be doing it holding the implementer's report, which is the anchoring the two passes were built to keep out.

**Both checkpoints spend the same budget, and it is not the fix budget** — they are one failure appearing at two moments, and *The protocol's own budget* below is what counts them, bounds them and says when the stage stops. A reviewer that cannot produce its own required output is not one whose PASS means anything, and re-dispatching until it does spends the owner's evening proving that.

- **PASS** → **re-read the requirement from the source and compare its hash first** (*Hash the requirement* above): a verdict earned against text that has since moved is `VOID`, not a pass. Then commit, and prove the commit is what was reviewed. `git diff HEAD~1 HEAD | git hash-object --stdin` compares the same two trees the reviewed hash was taken across, so it has to match **exactly**. **Any difference at all goes back for a fresh PASS before the push — there is no "only formatting" exception**, because an autofix does not guarantee it touched only layout, and even where it provably did, the verdict is no longer a verdict on the tree that exists. The whole gate rests on *the reviewed tree is the landed tree*; a size threshold on the divergence dissolves that claim quietly, which is the same shape as the bypass removed from the fingerprint gate. Running the gate's own fixer at step 2 above is what makes this check normally pass on the first try.
  - **A difference sends the commit back through *Restoring an unpushed commit to the review target*, below** — not straight to a re-dispatch, because a reviewer cannot be pointed at a commit.
  - **A re-review forced by the gate does not consume a fix round if it passes** — nothing was fixed, the gate moved the tree. If the reviewer blocks on something the autofix introduced, that is a real finding and it costs a round like any other.
  - Then `push → comment` below.
- **BLOCKED** → this is *an unfinished stage*, per the rule above, not a shortfall: the repo is not yet what the ticket asked for. Dispatch a fix, with the findings **verbatim** and nothing about which of them you found persuasive. Do not commit in between.
  - **A BLOCKED whose every blocking finding names the draft commit message alone does not consume a fix round.** The message is not in the code hash, so the tree the pass-one blocks were written against has not moved and there is nothing for an implementer to attempt. **Redraft it yourself** — *you do not fix it yourself to save a round* is about the code, and `SKILL.md`'s *the commit is yours* already makes the message your artifact — then send the corrected draft to the same reviewer for the `Claim audit` block alone, and commit on the fresh verdict that comes back rather than on the redraft — *a stage with no verdict has not been reviewed* has no exception here either. **It is also the one finding class that cannot be deferred to the completion test**: the push freezes the message, `start-or-resume.md` forbids rewriting a pushed commit, and a stage that lands with one of these open has landed it permanently. **If any blocking finding also names the tree, the round is charged as usual** and the redraft rides along with the fix.
- **VOID** → nothing was reviewed, and **what you do about it turns entirely on why** — *The protocol's own budget* below is the classification, and running it is what decides between retrying, stopping and starting over. The retryable causes increment that count and re-dispatch, each with its own remedy: a pass-one block missing at the part-two gate goes back as a whole first pass; one that moved by the final report goes to a fresh reviewer; a missing `Claim audit` is the only block a re-dispatch can repair alone; a contaminated pass one needs a reviewer that has not seen the report. **A decision that exists nowhere, a self-contradictory requirement, a tree the owner moved, and a tree you cannot account for do not retry at all.** **No `VOID` consumes a fix round** — nor does a finding the reviewer withdraws.
- **A finding that will not reproduce** → one exchange back to the reviewer, carrying your reproduction attempt in full. Suspect yours first: a fixture missing the property the finding was about looks exactly like a finding that was wrong. If the reviewer defends it, it stands.

### The protocol's own budget

**The fix budget bounds the code. Nothing bounded the loop.** Every path ending *"and it does not consume a fix round"* was right about the fix budget and silent about termination — so a packet that keeps coming back insufficient, a pass one that keeps arriving contaminated, or a fixer that keeps rewriting the reviewed tree could each turn indefinitely, legally, forever. **A stage that cannot be reviewed is not a stage that gets reviewed harder.**

So there is a second budget, and it is deliberately not the first one: **`protocol retry count`, four, kept on the ticket beside the fix rounds and never folded into them.** A protocol retry is the loop failing to *run* a review; a fix round is a review the code failed. Counting them together lets bad plumbing eat the budget the code needs.

**Five causes increment it, and they share the one property that makes retrying sensible: the failure is ours, and the same dispatch run again could succeed.**

- **`shape`** — a required report block missing at the part-two gate, or moved by the final report.
- **`packet`** — something that *is* in the sources and you failed to hand over. A mechanical extraction error, fixable by extracting it.
- **`contamination`** — the implementer's report reached pass one. Recoverable, with a fresh reviewer.
- **`tree-fixer`** — the commit gate's fixer moved the tree the verdict was on; *Restoring an unpushed commit to the review target* is the remedy. It keeps its own reason because that remedy is unlike the next one's.
- **`tree-moved`** — something else of ours wrote into the worktree mid-review: an implementer still finishing, a watcher or formatter daemon, a stray action by an agent in this loop. The remedy is ordinary — re-stage, re-hash both halves, re-dispatch — and the *two of the same in a row* rule is what stops an implementer that has not actually finished from being reviewed all night.

**Record the reason with every increment, and it is one of the five above — this list is the only one.** Nowhere else enumerates them, on purpose: the reasons are compared for equality by the *two of the same in a row* rule, so a second copy that has drifted by one member does not read as a typo, it reads as a breaker that does not fire. The count alone says a stage is going badly; the reasons say whether it is going badly *the same way*, which is the part worth acting on.

**Two of the same reason in a row escalates immediately — do not wait for four.** A second identical failure is already the evidence a third would produce: a fixer that rewrote the same tree twice does not rewrite it correctly on the attempt after that. **It fires before the count runs out and regardless of how much of it is left**, so a stage failing one way twice never reaches four.

**Four things never increment it, because retrying is the wrong response to all four.** They go straight to the owner, through the same escalation exit an exhausted fix budget uses:

- **A decision that exists nowhere.** The reviewer reports the packet insufficient and **cannot tell** whether the answer was on the ticket and you missed it — it is forbidden from reading the ticket. **You are not, so the classification is yours**: retrievable is a `packet` retry; genuinely undecided is a product question, and no number of re-dispatches will answer one.
- **A self-contradictory requirement** — the plan and the acceptance criteria asking different things, or an invariant ruling out a criterion. That is a defect in the ticket; `SKILL.md`'s drift branch is where it goes.
- **A tree the owner moved.** They edited the code under the review, so the diff now contains work the implementer did not write and the stage's scope is no longer settled. **Nothing failed, so nothing is counted** — but it does not auto-retry either: say what moved and ask what is in scope, then re-enter with the answer. An unattended run cannot confirm a scope, and re-reviewing a tree the owner is still editing is the requirement chase with the file contents substituted for the ticket.
- **A tree that moved and you cannot say what moved it.** **The mover has to be named from evidence, never from plausibility** — *the fixer probably did it* is an unknown mover with a story attached. An unknown one means **you do not know what a re-dispatch would be reviewing**, and dispatching anyway is how a review of something nobody identified gets recorded as a review of the stage.

**And a requirement that moved is not a protocol failure at all.** The owner edited the issue: the old verdict is void because the question changed, not because anything failed. It costs neither budget, and the stage restarts from part one against the current text. **But a second movement on one stage stops** — the same *twice is evidence*, from the other direction. Chasing a requirement still being written is a loop with an external motor, and the useful response is to say so and wait, not to spend the night re-reviewing drafts. **It stops as an escalation whose cause is neither budget** — nothing was spent, because nothing failed. Say that, and say what the owner has to do (settle the requirement, then re-enter), rather than reporting an exhaustion that never happened.

### Restoring an unpushed commit to the review target

**Three paths end with you holding a commit that has to be reviewed again — and a commit is not something `review-stage` can be pointed at.** Its target is a staged, uncommitted diff, per `rebuild-the-picture.md`'s invariant, and `git diff --cached` against a committed tree is **empty**, so such a dispatch hands a reviewer nothing at all. **Amending does not rescue it either: the re-review has to happen before the replacement commit exists.** So each of the three restores the target first, by the same steps:

1. **Confirm it is unpushed and uncited** — absent from `origin/<branch>`, named by no stage delivery comment. If it is either, stop: that is `start-or-resume.md`'s pushed-with-no-record case and it belongs to the owner. It is also `HEAD`, which the one-commit-per-stage and push-per-stage ordering guarantees; two unpushed commits means something else went wrong, and that is the owner's too.
2. **Save the commit message first.** It is the one thing the reset discards, and re-deriving it later is how a stage's message quietly stops describing what the stage did.
3. **`git reset --soft HEAD~1`** — the staged diff comes back byte-identical and nothing in the worktree moves.
4. **Re-confirm the tree**: `git status --porcelain`, nothing left unstaged.
5. **Re-hash both halves**, code and requirement, from the current sources.
6. **Create the review-state comment if none exists; otherwise set the existing one back to `dispatched`.** The third path in is *a resumed session finding an unpushed commit no review-state comment names*, so "set it back" is not always an available operation — there is nothing to set. Either way it ends up carrying the marker, the base SHA, both hashes, the round count, the protocol retry count and its reasons, and which recovery path caused the re-dispatch. **Clear the recorded pass-one blocks as part of this**: the review about to run is a new one, and a stale copy would be compared against a report it has nothing to do with. **The handback file is not cleared and not reused** — the new dispatch names its own, per *A dispatched agent's report is written before it is returned*, because a fresh review writing over the last one's file destroys a record the comment no longer holds either. **The two counts carry forward** — a restore is not a fresh stage. **If the create or the update fails, stop before dispatching part one** — a review running with no durable state is the memory gap this whole section exists to close, and it reopens the moment the write is skipped rather than retried.
7. **Run the gate normally** — part one, part two, verdict.
8. **On PASS, re-commit with the saved message**, then the post-commit identity check and the pre-push requirement check as usual.

The three paths in: the post-commit code hash differs from the reviewed one; the pre-push requirement check finds the requirement moved; a resumed session finds an unpushed commit no review-state comment names. **None of them consumes a fix round on its own** — the work is not what failed. A finding the re-review then raises does.

**This is the only place that sequence is written down.** Every caller points here instead of restating it: two copies of a recovery are two recoveries that drift, and the one that drifts is always the one nobody reads until a session has already died.

### The review state goes on the ticket at the dispatch, not at the first BLOCKED

**Everything between the dispatch and the stage comment is a window where the only record of the gate is in your context, and your context does not survive the session.** Waiting for a BLOCKED to start writing leaves the *commonest* path unrecorded: a stage that passes first time, gets committed, and dies before the push has a local commit, no comment, and **no evidence a review ever happened** — not the verdict, not which hash was reviewed, not whether the commit gate rewrote it afterwards, not whether a forced re-review was owed. The pushed-but-comment-failed case is worse: the recovery in `start-or-resume.md` posts the comment owed from the commit's own diff, and would be attesting to a PASS that nobody can point at.

So **post the review-state comment before part one goes out, and update it at every transition.** It is not a stage comment — it precedes the commit and may never become one — so it carries its own marker as its first line, which is also how a resumed session finds it:

```
<!-- deliver-ticket:stage-review:<stage-slug> -->
```

**`<stage-slug>` is `stage-<label>`, and `<label>` is the label the issue's Implementation Plan gives this stage, copied exactly as the plan writes it** — `stage-IV` where the plan's stage reads *Stage IV*, `stage-4` where it reads *Stage 4* — and its place in the plan's stage order when the plan labels nothing. **And where the plan does not carry this commit at all, it is `stage-<base>`: the short SHA of the commit this one builds on**, which is `HEAD` for as long as the work is staged. **That class is sanctioned, not an edge case** — `SKILL.md`'s four deviation conditions and `finish-the-ticket.md`'s *"you are not finishing, you are on another stage"* both produce commits no plan ever listed, and this ticket produced two of them. **The tree answers where the plan is silent, and it answers the same for everyone holding it**: distinct commits have distinct bases, a restored commit re-derives the same value because the reset puts `HEAD` back on it, and the value is the base SHA this comment records anyway. **The same branch takes a label that is not an identifier** — a slug goes into a path segment and into this comment's marker, so a plan that labels a stage in prose rather than in a word or a number has given it a title, and a title is not something to convert. **Copied, never converted**, because a plan is free to number two things and #385's does: six delivery stages labelled `Stage I`–`Stage VI`, and the fifteen material sections they land labelled `Stage 1`–`Stage 15`, on that plan's own stated ground that *"Roman numerals are delivery stages, digits are material, so no review-state comment can be ambiguous about which it names"*. **Converting that label to digits collapses its Stage IV onto its Stage 4** — the one distinction the plan drew, undone by the slug that was supposed to carry it. **And the conversion never bought anything**: what this rule is after is a slug *formed from something already settled* rather than invented, the plan's own label already has that property, and converting it adds nothing while costing the disambiguation. The plan's stages are the execution queue, adopted as written (`SKILL.md`'s *One sub-agent per stage — and the stage is the issue's to name, not yours to invent*), so the label is the issue's, settled before delivery began, and on that branch every session that can read the body forms the same slug from it. **Formed, never chosen**: a free-form slug is reproducible only by the dispatcher that invented it, and *A dispatched agent's report is written before it is returned* names its directory from this slug **in the window before this comment exists** — so a slug only this comment could supply leaves that window nothing to derive from, which is the one window the derivation is for. **Re-ordering does not move it**: a stage parked as a patch and re-applied per *Before you commit* keeps the label the plan gave it, so its directory is the same one whenever its review actually runs.

**The marker stays the first line and the role word is the first line that renders.** GitHub shows an HTML comment as nothing, so the two never compete for the slot: the marker is for the session that comes back and for the `gh api` lookup that finds it, the role word is for whoever is scanning the stream — `SKILL.md`'s *The ticket is the record, not just the target*.

It carries, and keeps current:

- **`state`** — one of `dispatched`, `pass one recorded, part two unsent`, `blocked (n of 2 fix rounds spent)`, `passed`, `committed <sha>, awaiting push`, `landed <sha>`, `escalated`. **The second exists because this file now requires a write between the two parts**: without it, a session dying in that window is indistinguishable from one that died before part one came back, and the difference is whether a first pass has to be redone.
- **The base SHA, the code hash, and the requirement hash** the current round was reviewed against.
- **The `requirement movement count`, 0 or 1, and the requirement hash recorded at each movement.** The rule that a second movement stops needs a memory of the first, and the hash above is not one — it is overwritten by the restart. Without this the chase survives a session boundary: every resumed session reads a requirement that has moved zero times, and restarts again.
- **The round number against the budget — which increments when a fix is *dispatched*, never when a BLOCKED *arrives*.** The budget bounds attempts at the code, and a verdict nobody has answered yet is not an attempt: a stage sitting at its first BLOCKED with no fix sent has spent **`0 of 2`**, and the sequence in `SKILL.md` is the whole of it. **Recording it at the verdict costs the stage a round it never used** — and costs it silently, because the number then reads as spent to every later session, including the one deciding whether to escalate. #371's stage 5 wrote `1 of 2` before any fix existed and afterwards could not tell its own label from the rule; that is the state this sentence exists to make unreachable. And — **counted separately, never folded into it** — **the `protocol retry count`, 0 to 4, with each retry's reason** — one of the reasons *The protocol's own budget* defines, named there and **not restated here**, because a second copy of a list whose members are compared for equality is a list that will disagree with itself (`CLAUDE.md`'s *a string list is one contract per member*). This copy had already lost one. A protocol retry is the loop failing to run a review; a fix round is a review the code failed, and one number cannot carry both. The reasons are what the *two of the same in a row* rule reads. **Write it before the re-dispatch, not after** — a resumed session that cannot read it restores a limit that has silently reset, which is the same defect the round count is on the ticket to avoid.
- **The report path every dispatch on this stage named, against the dispatch that named it** — the implementer's report, and the reviewer's pass-one handback and final report, per *A dispatched agent's report is written before it is returned*. **Written at that dispatch**, and the implementer's the moment this comment exists, since its dispatch runs first. The directory can be derived from the issue and the stage slug; which file came from which dispatch cannot, and this is the only place that says. It is a machine-local path and it is recorded here so a session that never received the message can still read what was written.
- **The pass-one handback's four blocks, verbatim** — `Claimed scope`, `Axes in play`, `Dimensions crossed`, `Verified` — recorded when the first pass comes back and before part two goes out. The final report is compared against this copy; held only in the session, the freeze on those blocks is unverifiable the moment the session ends. **The copy belongs to the reviewer that wrote it** — a replacement doing its own pass one overwrites it, because the freeze protects a reviewer against its own contamination and a fresh reviewer has nothing yet to be contaminated by. Comparing a replacement's report against its predecessor's blocks would fail on every honest difference between two independent readings.
- **The reviewer's findings for each round, verbatim**, and what each fix changed.

The hashes are what make a resume precise rather than approximate: a staged tree matching the last round's code hash means that verdict still stands; one that differs means a fix landed and its re-review did not, so that round is already spent.

**Locate it by the marker, not with `--edit-last`.** `gh issue comment --edit-last` targets your most recent comment on the issue, which is the wrong one as soon as anything else has landed since — and on this ticket something will have. `gh api repos/:owner/:repo/issues/<n>/comments` filtered on the marker gives the id, and `gh api -X PATCH repos/:owner/:repo/issues/comments/<id>` updates it.

**Close it out only once the stage has actually landed** — pushed, with its stage comment posted — by setting `state` to `landed <sha>`; an exhausted budget closes it as `escalated`, pointing at the escalation comment. **A review-state comment left open reads as a stage still mid-review**, which is exactly the state a resumed session is trying to identify. The closing edit also records **how many rounds the stage spent, and whether it passed first time** — the one measurement this loop produces for free, and the only way to tell later whether the gate is catching things or just costing rounds.

**Two fix rounds is the budget**, counted as *The review state goes on the ticket* above counts them — by fixes dispatched, not by verdicts received. When the second re-review still returns BLOCKED, **the stage escalates and nothing commits** — and this is the exit *The protocol's own budget* uses too, so **the comment says what ended the stage**, because the ways it can end are unalike and what the owner does next differs with each. An exhausted **fix** budget is evidence about the code, the plan or the ticket. An exhausted **protocol** budget is evidence about the loop, and re-running it unchanged reproduces it. **A question only the owner can answer** — an undecided decision, a self-contradictory requirement, a tree nobody can account for — spent no budget and is waiting on them, not on another attempt. **And an external change** — the requirement moved twice, or the owner edited the tree — spent nothing and broke nothing: the work is intact and what is owed is a target that holds still.

- **Park the work where it survives the session.** `git diff --cached > <patch>` into the scratchpad or a `mktemp -d` — **never inside the worktree**, which would add an untracked file to the very diff under review. Leave the worktree staged and otherwise untouched.
- **Comment on the ticket** — a new comment, because this one has to reach the owner: the stage, the base SHA, where the patch is, what the owner has to decide, and **a link to the review-state comment for the round-by-round detail rather than a second copy of it.** The findings are already there verbatim; restating them creates two accounts of the same rounds that will differ. Then set that comment's `state` to `escalated` and stop — no commit, no next stage. `start-or-resume.md` reads both to recognise this state on the way back in. **That order is the citation rule and not a convenience**: the pointer to the escalation goes into the review-state comment once the escalation has been posted, never before — `SKILL.md`'s *The ticket is the record, not just the target*, whose incident this pair is.
- **A stage that fails three reviews is evidence about the plan, the packet or the ticket** rather than about the code, and a fourth attempt at the code is the one response that cannot help. If the ticket itself turns out to be wrong, `SKILL.md`'s drift branch is where that goes.

## Push before the stage delivery comment, always

The order is **verify → review → commit → push → comment**, every stage, no exceptions — and **the comment it names is the stage delivery comment**, the one per commit below. **The review-state comment is not that comment**: it is the gate's own durable state, it goes up before part one is dispatched, and it is updated at every transition including this push. Read unqualified, "no comment before the push" and *the review state goes on the ticket at the dispatch* are two orders that cannot both be carried out; this is which one governs which comment.

A delivery comment citing a SHA that only exists in the local worktree is citing something a reader clicking through cannot open — and on a delivery that can run for hours, local-only is one crashed session away from being the only copy that ever existed.

**Re-check the requirement hash before the push, not only before the commit.** The commit runs the gate's whole suite, which takes minutes, and the ticket can move inside them: a body revision, a new owner decision, a criterion that shifts. Then the code that lands is exactly what the reviewer read and **the requirement it lands against is not** — which the post-commit identity check cannot see, because it only compares trees. So re-read the sources and compare before pushing, on a resumed `committed <sha>, awaiting push` exactly as on the straight path. A difference stops the push, and the commit goes back through *Restoring an unpushed commit to the review target* above before part one can be dispatched at all: `VOID`, no fix round consumed.

**Push is a checkpoint because it is the step that makes the SHA public and citable.** Past it, `start-or-resume.md` forbids rewriting that commit — so nothing after the push can quietly correct what the push published, which is precisely the property that makes the near side of it the last place a check is free.

**If the push fails, the stage has not landed.** Do not post the comment claiming it has. Resolve why it failed — a moved remote branch is the likely cause — and push before writing anything.

**If the push succeeds but posting the comment fails, do not start the next stage.** Re-post the comment for the commit that is already public first. A resumed session finds this exact state by diffing `git log <branch>` against `git log origin/<branch>` and against what the comment stream actually names — see `start-or-resume.md`. A pushed commit with no comment naming it is not a new stage to build; it's a comment owed on one already built.

## The comment, one per commit

Post it as the commit lands, not in a batch at the end. **It opens with the role word** — `SKILL.md`'s *The ticket is the record, not just the target* — and then carries five things; the last one is the one that gets skipped:

**1. What landed, and the commit.** The short SHA and one line on what is now true that was not. Not a file list — the file list is in the diff.

**2. What you ran, and what it showed.** The command and its result. `2134 tests green` is evidence; *"tests pass"* is a claim about evidence. Where you rendered an artifact to check it, say which artifact and quote the line that settled it.

**3. Which claims are measured and which are reasoned.** Mark them. A mechanism you inferred from reading is worth writing down and is not the same as one you executed, and only the label tells a later reader which ones are still owed a run.

**4. The review.** That it returned `PASS`, on which base, code hash and requirement hash — and if it took rounds to get there, what each round's findings were and what closed them. **A stage that passed first time says so explicitly.** This is the only durable record that the gate ran at all: a commit and a comment look identical whether a reviewer cleared them or nobody was ever asked, which is exactly the gap `start-or-resume.md`'s fingerprint gate exists to close one level up. Anything the reviewer filed as **FOLLOW-UP** is not closed by the PASS — it becomes a shortfall below, something the owner rules outside, or **an observation outside this purpose**, by the ordinary rules. **What selects the third is relatedness, and the membership instrument is what measures it**: if the instrument bounding this stage's frontier admits it, it is in the class and it is a shortfall — and *Writing a shortfall*'s Outside branch then decides whether the owner rules it out. If the instrument does not name it, it is unrelated, and unrelated is what an observation is. **Importance enters neither test.** So the third is not a softer shortfall: it is not this ticket's to carry, it never enters the shortfall list, and it never gates the finish. **Record it in this comment under the heading `Observations outside this purpose`**, with its address and its measurement and no case for taking it, and `finish-the-ticket.md` collects it into the closing comment's one list under that same heading. **That is the only durable channel it has** — the review-state comment closes out at `landed`, and the closing comment does not exist until after the merge.

**5. Shortfalls.** Everything you noticed and did not close in this commit, each with an address — file and line, or the command and the output. **Repeat the ones still open from earlier comments.** A shortfall named once and never mentioned again is indistinguishable from a shortfall that was fixed.

State explicitly when there are none: *"No shortfalls open."* Silence reads as "nobody looked".

## Writing a shortfall

**Name the thing that is wrong, its address, and whether it is inside this ticket.**

- **Inside** — you close it, in a later commit on this ticket. Say what you intend to do, or say you do not know yet.
- **Outside** — it predates the ticket, or it changes what the tool asserts, or it would be needed even if this ticket had never existed. **Say that it is outside, name it fully enough to act on, and stop.** Do not open a ticket. Do not fix it either; a fix the ticket did not ask for is invisible to whoever reads the diff expecting only what was asked.

**The test for "outside" is not how big it is.** A one-line fix to something that predates the ticket is outside; a two-day rewrite the ticket's own goal requires is inside.

**Uncertain? Write it as a shortfall and say you are unsure which side it falls on.** The owner reads these. An unsure note costs a sentence; a wrong absorption costs a diff nobody can explain.

## Then the next commit

Take the open shortfalls first, unless a staged delivery blocks them. Each commit that closes one says so in its comment, naming which — so the list shrinks visibly rather than quietly.

**A shortfall you decide not to fix is not closed by deciding.** It stays open and named until the owner rules it out of scope, and the ticket does not finish while it stands.
