# Starting or resuming a ticket

**Trigger:** the skill loads. Every time — a fresh "do #204" and a resumed session both read this before anything else happens, because from inside the session there is no way to tell which one this is without doing the reading first.

## Read before you decide anything

**The issue body and every comment, in full** — not the latest comment, not a summary of the ticket someone gave you in the prompt. The comment stream is deliver-ticket's own record of every stage that landed, every shortfall opened and closed, and every reason a decision went the way it did. Skipping to the bottom loses the shortfalls that have no address anywhere else.

**`git fetch origin --prune` first — every time, before searching or branching.** A stale `origin/main` and a stale set of remote-tracking refs both look identical to "nothing's there" from inside a session that hasn't talked to the remote yet, and that's indistinguishable from an actual fresh start until you've fetched.

**Then search for what already exists, before assuming there's nothing.** `git worktree list`, `git branch --list 'ticket/<n>-*'`, **and `git branch -r --list 'origin/ticket/<n>-*'`** — the remote-tracking search matters because a worktree from an earlier session may have been cleaned up locally while its branch is still live on the remote, and only the fetch above makes that branch visible at all. These find deliver-ticket's own worktrees and branches — they always carry the ticket number, per the naming rule in *New work gets a new environment* below, even though this repo's other feature branches read by outcome instead (`CLAUDE.md`'s convention for everything that isn't this skill's own bookkeeping). `gh pr list --search "<n> in:body"`, or by title, and a commit-message grep for the number cover the case where the branch predates this convention or was made by hand outside this skill.

## Reconstruct the state; don't assume it

Cross-reference what the comments claim against what the branch actually contains. **A comment saying a stage landed and a commit that actually landed are two different kinds of evidence** — `SKILL.md`'s own *How you verify* applies to this ticket's history exactly as it applies to a sub-agent's claim, and "the last comment said done" is the implementer's kind of evidence, not yours until you've checked it. `git log <branch> --oneline` against the SHAs the comments cite is the check.

From that comparison, build the same list `finish-the-ticket.md`'s completion test needs at the end — build it now, at the start, instead:

- **Which stages have actually landed**, each checked against its comment rather than assumed from it.
- **Which shortfalls are still open** — every one the comment stream ever named and never later said was closed.
- **A pushed commit with no delivery comment naming it is not a stage to redo — it's a comment owed.** `deliver-a-stage.md`'s ordering runs from the verify through to the next dispatch, and *Push before the stage delivery comment* is the one place it is written out; a resumed session is exactly where a run that died partway along it turns up. **Post the missing comment from that commit's own diff and from your own verification of it** — there is no per-commit verdict to read it off, because the ticket's one review runs once, at the end, over all of this together. Then **pick that order up where the run died and run it out** — the comment is not its last step: `deliver-a-stage.md`'s *Nothing that closes a unit of work is finished until the next thing is dispatched* is, and what it dispatches is the next stage, or the completion test when no stage remains.
- **Any open review-state comment is migrated to the current field names before you read anything else off it — including which worktree or commit state you are in.** `deliver-a-stage.md`'s durable fields have been renamed and added to while tickets were in flight, so a comment written under the previous names is a normal thing to find. **There is one per ticket and it goes up at the completion test's review dispatch** — `deliver-a-stage.md`'s *There is one review state per ticket, not one per stage* — so **finding none mid-ticket means the ticket has not reached the completion test, not that a gate was skipped**, and **the two branches below that do read one — the staged-worktree branch and the local-unpushed-commit branch — read different fields off it.** Migrating inside one of them leaves the other reading a format that is not there, silently starting a budget at zero and losing exactly the history the same-reason breaker needs. Convert, write back, then branch:

  - **`shape VOID count: n`** → `protocol retry count: n`, with `shape` as the reason for each of the `n`. **Two of them migrates into an already-terminal state**: two of the same reason in a row is the early circuit breaker, so that stage escalates rather than being re-dispatched. That is the current rule applied to real history, not an artefact of converting — a stage that failed the same way twice is what the breaker is for, whenever it happened.
  - **Neither count present** → the comment predates both budgets; start each at 0. It also carries **no recorded pass-one blocks**, so a `dispatched` state re-enters the gate from part one rather than comparing a final report against a copy that does not exist.
  - **No `requirement movement count`** → 0. A movement that happened before the field existed left no trace, and the current hash cannot be read backwards into one.
  - **More than one `state:` field** → **count only the ones no fence holds; of those the header block's is the state, and every later one is a round already over.** **A fenced `state:` was never a state** — `deliver-a-stage.md`'s *A `state:` line the comment quotes is not a second state* is where that is decided, and a migration that reads a reviewer's quoted field as a round already over writes a transition the stage never made into the one record a resume trusts. #379 has eight such comments and seven disagree first-to-last — `landed <sha>` in the header against `dispatched` in the last log line — so *"the `state:` line"* is not something to read. **None of its 37 fields is quoted material**, so the fence subtracts nothing from that count; it starts mattering on the first comment that records a finding quoting one. **Take the header's and leave the log exactly as it stands**: the conversions above are renames, and the log is the record. `deliver-a-stage.md`'s *The review state goes on the ticket at the dispatch, not at the first BLOCKED* is where the one-field format is written.

  **Write the migrated comment back before dispatching anything**, so the migration happens once and every session after this one reads a single format. **A closed comment — `landed <sha>` or `escalated` — is left alone**: it is a record, nothing will read a budget off it again, and rewriting history to a newer schema is how a record stops being one.
- **A staged, uncommitted worktree is either a stage the dispatcher never finished verifying or the ticket's one review in flight, and the review-state comment is what tells them apart — search the comments for `<!-- deliver-ticket:stage-review:` before deciding anything.** `deliver-a-stage.md`'s gate keeps the round count there precisely because a session's own memory of it does not survive the session:
  - **A review-state comment still open** → the ticket's one review is in flight; resume at the round it names. **The budget continues from that number; it does not reset because a new session started**, which is the whole reason the count is on the ticket. **A staged tree is not what that review is reading** — it runs over committed history at the branch tip — so something wrote into the worktree while it was in flight: that is `tree-moved`, and *The protocol's own budget* holds both its remedy and the count it increments. The reviewer's findings are in that comment, verbatim — a re-dispatch reads them rather than rediscovering them. **Read the `protocol retry count` and its reasons from the same comment and continue from both**: it is a separate number from the round count on purpose — a protocol retry is the loop failing to run a review, not a review the code failed — so a resume reading only the rounds restores a limit that has silently reset. **The reasons matter as much as the number**, because two of the same in a row escalates before the count runs out, and a resumed session that reads the count alone cannot see that it is already there. **Read the `requirement movement count` too** — a stage that has already restarted once for a moved requirement stops on the second movement instead of restarting again, and the requirement hash cannot tell you that, because the restart overwrote it. **And `pass one recorded, part two unsent` is its own state** — the first pass is done and copied into that comment, so what is owed is part two, not a repeat of pass one; only if the reviewer is gone does a replacement start from part one, and its own handback then replaces the recorded copy.
  - **An escalation comment** → the budget is exhausted and this stage is not yours. The work exists, was rejected for stated reasons across every round, and the branch it is committed on is named there. **It does not resume on its own** — the escalation was addressed to the owner and the answer comes from them. Re-dispatching it blind produces a third attempt at something two reviews already named. **Read which cause the comment names**, because one of the three is not an exhaustion: a stage stopped for a requirement that moved twice has spent no budget and has its work intact, and what unblocks it is the owner settling the requirement — not a decision about code that was never found wanting.
  - **Neither** → the ticket has not reached its completion test, so this is a stage the dispatcher never finished verifying rather than a review that was skipped. **Verify it yourself and commit it**: stage, run `npx lint-staged`, re-stage, and run `deliver-a-stage.md`'s *Before you commit* over what comes out — that is the whole bar a stage lands on. **No round has been spent and none was owed**, because the ticket's one review is dispatched once, at the end, over all of it.
- **A commit that exists locally and not on the remote is the window between your own verification and the push, and what is owed is the push and the comment.** It no longer follows a PASS — the ticket's one review runs once, after the last requirement lands — so the review-state comment says only whether that review is already in flight, and that is the whole of what it changes here. Look it up by marker before touching it:
  - **`committed <sha>, awaiting push` or `passed`** → the gate cleared it and the push is what is owed. Confirm the commit's own tree still matches the code hash that comment records — `git rev-parse <sha>^{tree}`, never a hash of a diff and never through a pipe, per `deliver-a-stage.md`'s *What you verified, and against which tree* — **and re-check the requirement hash** per `deliver-a-stage.md`'s pre-push rule, then **rejoin its landing order at the push and run it out** — closing this very comment is one of the steps past the delivery comment, and a resume that stops at the delivery comment leaves it standing as a live review. **A code mismatch is not a voided verdict**, because no verdict precedes this commit — it means the tree that landed is not the tree that hash was taken on: the commit gate's own fixer rewrote it on the way in, or the hash belongs to a round this commit is not part of. Then what you verified and what the push would publish are two different trees, and the tree that landed is what has to be verified. A requirement mismatch means the ticket moved while this sat. Either one is what is owed instead of the push.
  - **No review-state comment naming it** → the ordinary mid-ticket case, not a commit that dodged anything: the comment goes up at the completion test, so nothing was ever going to name this one. **Push it, then post the comment owed above**, written from the commit's own diff and your own verification of it. What certifies it is the ticket's one review, later, over all of it at once.
- **A pushed commit that no review-state comment names is the ordinary mid-ticket state, not a stop.** The comment goes up at the completion test's review dispatch, so until then no commit on this branch is named by one and none was meant to be — what such a commit owes is the delivery comment above. **What still stops is work reaching `main`'s history with no record at all**: a ticket carrying no valid fingerprint, which is *The ticket has to already be a ticket, not a direction* below and stops before the next commit whatever else is true; and **a ticket whose one review never ran, being walked past on the way to a pull request** — `SKILL.md`'s *a ticket with no verdict has not been reviewed*, earned at `finish-the-ticket.md`'s step 5. **Neither is repaired by reviewing something after the fact**, which is the laundering this gate exists to prevent. And neither is what a mid-ticket commit with no comment naming it is: the gate there has not been skipped, it has not been reached.
- **Which commit is `HEAD` of the existing branch**, and how far behind `origin/main` it is — being behind is not, by itself, something to fix mid-ticket; see *New work gets a new environment* for what is and isn't allowed about it.

**A stage the comments describe as landed is not redone.** Re-running a finished stage through a fresh sub-agent produces a second attempt at something already true, and the two rarely agree on the seam — that's how a resumed ticket ends up with a commit undoing part of an earlier one for no reason a later reader can find.

## New work gets a new environment; resumed work reuses the one that exists

**One worktree per ticket**, per `SKILL.md`'s Repo facts — but *per ticket*, not per session. If the search above found an existing **local** worktree or branch for this ticket, that is the one to continue in, not a second `git worktree add` beside it. Two worktrees for one ticket is exactly the failure the Repo facts note already names: commits landing on the wrong one because two sessions each believed they owned the checkout.

**A branch that only turned up on the remote — `origin/ticket/<n>-*` with no local counterpart — is a resume, not a fresh start, and the recovery is to rebuild the local half from it, not from `origin/main`.** This is what the remote-tracking search above exists to catch: a worktree from an earlier session got cleaned up (or was never on this machine) while its branch, and every commit already pushed and cited in a comment, is still live on the remote. `git worktree add <path> -b ticket/<n>-<slug> origin/ticket/<n>-<slug>` creates the local worktree and branch **from that existing history** — branching it from `origin/main` instead would silently discard every commit the ticket already has, which is indistinguishable from data loss to whoever reads the comment stream afterward and finds the branch doesn't contain what it says it does. Once rebuilt this way, proceed exactly as *Reconstruct the state* above.

If nothing exists anywhere — no local worktree or branch, no matching remote branch either — this is a genuine start, and *The ticket has to already be a ticket, not a direction* below has to pass **before** any of the following: branch from the `origin/main` tip the fetch above just resolved — not from whatever the session's own working directory happens to be on, and not from a local `origin/main` that predates that fetch — create the worktree, `npm ci` inside it, and record where it branched from the same way the first stage comment will need to.

**Name both the branch and the worktree directory with the ticket number**: `ticket/<n>-<slug>`. This repo's other branches read by outcome instead, but that's exactly what defeats a resume here — an outcome-named branch says nothing about which ticket it belongs to until a commit or comment references the number, and a session interrupted before either exists leaves nothing to search for. The number in the name is what *Search for what already exists* above depends on.

**Being behind `origin/main` mid-ticket is a judgment call, not a mandate to fix** — `deliver-a-stage.md`'s stage-order rule already covers the one case where updating is forced (a commit gate failing on work belonging to a stage not yet started).

**Before any stage has landed — no commit pushed and cited in a comment yet — rebasing onto `origin/main` is fine.** There is nothing yet a rewrite could invalidate.

**Once one has, only `git merge origin/main` is allowed, for the rest of the ticket's life. Never rebase, and never force-push, either window.** A rebase replays every commit unique to the branch, not just the new ones being caught up — so it rewrites the SHA a comment already cited even when the only intent was to move the branch's own base forward, and there is no way to rebase selectively enough to avoid that once a cited commit exists. `deliver-a-stage.md`'s push-before-comment rule exists to make that SHA a stable, public reference; a merge commit brings `origin/main` in without touching it, which is why merge is always the safe operation and rebase, past this point, never is.

## The ticket has to already be a ticket, not a direction

**This is a hard gate, checked on every load — fresh start or resume, every time, with no exception inferred from a commit already existing.** A pushed commit and a cited comment prove a stage landed; they do not prove a gate ever ran, since they look identical whether this ticket went through shape-ticket, predates that requirement, or was built by hand outside either skill entirely. Checking every time costs nothing extra, though: the issue body is already being read in full per *Read before you decide anything*, so this is a scan of text already in hand, not a new investigation.

**Look for shape-ticket's fingerprint — two HTML comments, first thing in the body:**

```
<!-- blueprint-shape-ticket:v1 -->
<!-- grounded-at:<sha> -->
```

Three things have to hold, in order: the `v1` marker is present and is a version this file recognizes (currently only `v1` — a different version means shape-ticket's contract moved and this file is the one that's stale, not the ticket); `<sha>` is present and resolves to a real commit (`git cat-file -e <sha>^{commit}`, after the fetch above); and `## Goal`, `## Implementation Plan`, `## Acceptance Criteria` are all present with actual content beneath them, not just the heading. **The fingerprint checks that the shape-ticket process actually ran; the headings check that its output has the right shape — check both, because either alone is fakeable or accidental in a way the other isn't.** A hand-written issue can copy three heading names without ever having been shaped; a fingerprint with a corrupted or invented SHA fails the resolve check even if it looks right at a glance. This is a process check for a solo, non-adversarial pipeline, not a security proof — someone could still hand-copy the fingerprint itself onto a real SHA, and that's an accepted gap here, not one this gate is trying to close.

**If the fingerprint is missing or invalid, stop before any further commit — regardless of what *Reconstruct the state* found.** There is no exception this skill grants for continuing without one, and no "confirm to proceed anyway" this file offers. A ticket without a verifiable fingerprint is not one deliver-ticket builds, whether that would be the very first commit or the next one on a ticket that already has several.

- **Nothing landed yet** → stop before creating a branch or worktree. Comment: which part failed (no fingerprint, an unrecognized version, an unresolvable SHA, or a missing/empty heading), that deliver-ticket won't build against an issue that isn't verifiably shape-ticket's own, and the recovery path below. **If a stage-less worktree already exists from an earlier, also-rejected attempt at this same ticket, remove it** per `finish-the-ticket.md`'s *Cleaning up* — there's nothing on it worth keeping.
- **A stage already landed** → stop the same way. Comment that this ticket carries real work but no verifiable fingerprint, and that continuing it through this skill isn't something deliver-ticket does — from before this gate existed, from an older version of this skill, or from outside it entirely, the reason doesn't change the answer. **What happens to that work is the owner's decision, made outside this flow** — finishing it by hand, or closing the issue and letting a reshaped one account for what already exists — not a one-time exception this skill grants and then continues past. Naming the situation is this skill's job here; resolving it is not.

**If the fingerprint is present and valid, trust it — this is where the cost of re-deriving shape-ticket's own work actually gets cut, not before.** `<sha>` is the commit the plan is grounded on; `git diff <sha> origin/main` says what's moved since. `SKILL.md`'s *Before the first commit, read what the tool already promises* covers reading against that diff instead of an open-ended search — including the case where the diff shows a citation's premise gone rather than merely moved, which is its own stop-and-reshape path, not something to re-verify and carry on past — and *You dispatch the work; you do not type it* covers adopting the issue's own stages instead of re-cutting them.

**Name the recovery path in the rejection comment — it isn't obvious from either skill alone.** For a missing fingerprint, there is no in-place fix: `shape-ticket` won't edit an issue that never carried its fingerprint in the first place, because that issue never went through it — the path back is the owner closes this issue, naming why, and re-runs `shape-ticket` on the direction, which investigates afresh and files a new issue superseding this one via *Related work*. Deliver-ticket is then invoked again, on the new number.

**A plan `SKILL.md`'s drift check finds invalidated is not automatically the same recovery — it branches on whether the goal moved and whether a landed stage would be invalidated:**

- **The goal is unchanged, and every stage already landed still holds under the fix** — say so in the comment, name it a plan or acceptance-criteria gap rather than a shortfall, and stop there. The owner runs `shape-ticket` on this same issue number for an in-place revision instead of closing it — `shape-ticket`'s own `revise-an-in-flight-ticket.md` is the narrow exception to "never edits an existing issue," scoped to exactly this case. Once the issue is updated, resume this same ticket: the branch, the worktree, and every landed commit stay exactly where they are, and nothing already delivered is redone.
- **The goal changed, or the fix would invalidate a stage already landed** — the close-and-reopen path above, unchanged: the owner closes this issue, naming why, re-runs `shape-ticket` on the direction, the new issue supersedes this one via *Related work*, and deliver-ticket is invoked again on the new number.

Leaving either branch unsaid makes both skills individually consistent and jointly a dead end; say which one applies so the owner doesn't have to reconstruct it.
