Run npx @kekkai/blueprint init --authoring to adopt @kekkai/blueprint in this repo.

最後一步（必做）：把你對 @kekkai/blueprint 這次導入體驗的 feedback 寫進
repo 根目錄的 blueprint-field-feedback.md（繁體中文）。用這個大綱，**標題一字
不差**——harness 是照標題把「要修的」挑進 issue 的，標題對不上它只能整份貼：

    ## 好用的
    ## 卡到的
    ### 查證後撤掉
    ## 拿不準的
    ### 沒立場，我自己發明
    ### 有立場，我照做

檔案最後一行也必寫，給 harness 讀（沒有就寫 0）：

    field-verdict: blocked=<卡到的條數> invented=<沒立場條數> withdrawn=<撤掉條數>

**只有「卡到的」跟「沒立場，我自己發明」會進 issue**，因為 issue 是要修的清單。
其餘三段留在本地報告——但**照寫**：撤掉的紀錄是你這輪到底有沒有查證的證據，
也是我們判斷回報品質的主要依據，寫得越清楚越有用。三段都空、`blocked=0
invented=0`，就是這輪通過，harness 連 issue 都不會開。

各段的規則：

- **好用的** —— 哪些設計真的有幫到你。
- **卡到的** —— 工具本身的問題（不是這個專案的問題）。每條除了 repro
  （指令 + 預期 vs 實際），還要寫出**實際代價**：被擋了多久、做錯了
  什麼決定、或被迫讀了什麼內部。沒有實際代價的觀察不屬於這段——
  降到「拿不準的」或撤掉。**寧可空白也不要硬擠**：「勉強算」「理論上
  可能誤導別人」都不算卡到；「沒有」＋一兩條「查證後撤掉」的紀錄，
  比硬擠一條更有價值，也是完全合格的回報。
  **但有一類例外，不受「實際代價」這關過濾：工具講的話跟事實不符，
  或它自己前後矛盾。** 這兩種一律報，就算它這次沒絆到你、就算你繞過去了。
  理由很簡單：代價是「你這一輪的性質」，不是「工具的性質」——同一句錯話
  下一個人可能就付了代價。這類請附上你怎麼驗的（跑了什麼、預期什麼、
  實際什麼；或矛盾的兩句各自引出來），驗證本身就是這類回報最有價值的部分。
  **這關有下限**，不然「任何一句話都可以再精確一點」會讓這段永遠非空。
  下限是：你要指名**互相不符的兩樣東西**，而且**兩樣都是現成、可查的**——
  某個指令的實際輸出、磁碟上的檔案、或同一份文件的另一行。以下三種都不算，
  一律歸「拿不準的」：
  - **只有一樣**：工具講了 X，你覺得 X 不夠精確、應該再補一句。
  - **工具「沒講」**：你不知道某個狀態該怎麼辦。這條講的是「講錯」不是
    「沒講」；沒講屬於「沒立場，我自己發明」。
  - **兩樣裡有一樣是你的預期或你的讀法**。要拿工具自己的輸出、或它自己的
    另一句去對，不是拿你以為它該說什麼去對。
- **查證後撤掉**（`## 卡到的` 的子段）—— 一度想報、去查了、發現站不住的。
  連「怎麼驗的」一起寫。這段不進 issue，但它是這份回報最能證明你有查證的
  部分，別省。
- **拿不準的** —— 你自己拍板、而工具沒有替你拍的決定。分兩個子段，因為這
  兩種的意義完全不同，而你是唯一知道自己是哪一種的人：
  - **沒立場，我自己發明** —— 工具對這件事完全沒有立場，你只能自己想一個
    出來。**這才是缺口**，寫清楚你發明了什麼、依據是什麼。沒有就寫「沒有」。
  - **有立場，我照做** —— 工具講了它的立場、你依著它決定。這**不是缺口**——
    治理工具本來就該把架構決定交還給人。寫一兩句帶過就好：什麼決定、你依的
    是哪句話。這段的價值在於「還有哪些事等 owner 拍板」的清單。
  同一關自檢兩段都適用：**那個立場是不是本來就在你眼前的管道裡**（playbook、
  catalog、指令輸出、錯誤訊息、生成檔的 inline comment）？在的話就是
  「有立場」，不是缺口。這段也**寧可薄不要硬擠**——整段都是「有立場」是
  完全合格的回報。硬把「我照著做」寫成「工具沒接住」只會讓真正的缺口被淹掉。

評判基準先講明：blueprint 是「約束 AI 開發不失控」的治理工具，**嚴謹本身
是它的目的**——「限制太嚴」「對小 repo 太隆重」不是問題，不用回報；工具
「講不清楚、自我矛盾、逼你逆推內部、或給錯資訊害你判斷錯」才是問題。
每條「卡到的」先過一關自檢：**答案是不是本來就在你眼前的管道裡**（docs、
playbook、schema sketch、錯誤訊息）？自己漏看、漏做的不是工具問題，
撤掉、不要報。誠實寫，不用客氣；沒有踩點就寫沒有。
